## 运行时架构图

```mermaid
flowchart TD
    U[用户消息] --> SP[SessionPrompt.loop()<br/>packages/opencode/src/session/prompt.ts]
    SP --> RL[runLoop while true]
    RL --> AG[Agent.Service<br/>加载 agent、权限、steps]
    RL --> TR[resolveTools + ToolRegistry]
    RL --> IN[Instruction.system<br/>AGENTS.md + CLAUDE.md + 自定义 instructions]
    RL --> SY[SystemPrompt.environment + skills]
    RL --> MM[MessageV2.toModelMessagesEffect<br/>把会话历史转换成模型消息]
    MM --> LLM[LLM.stream<br/>packages/opencode/src/session/llm.ts]
    LLM --> PR[SessionProcessor.process]
    PR -->|文本 + reasoning + tool 事件| MSG[assistant 和 tool parts 持久化到 session]
    PR -->|tool call| TOOL[内置工具 + 插件工具 + MCP 工具]
    TOOL --> PR
    PR -->|finish = tool-calls| RL
    PR -->|overflow| CMP[SessionCompaction.process]
    CMP --> RL
    PR -->|finish = stop| END[返回最终 assistant message]

    RL -->|subtask| TASK[Task tool]
    TASK --> SUB[子会话或子 Agent]
    SUB --> RL
```

OpenCode 的运行时核心并不是单独一个 `Agent` 类。真正的控制中心是 `packages/opencode/src/session/prompt.ts` 里的 `runLoop()`，再配合 `SessionProcessor`、`LLM.stream()`、`ToolRegistry` 和 task tool，一起组成完整执行路径。

## 核心 Agent Loop

循环入口位于 `packages/opencode/src/session/prompt.ts:1400`。

```ts
function runLoop(sessionID) {
  let step = 0

  while (true) {
    const msgs = loadMessages(sessionID)
    const lastUser = findLastUser(msgs)
    const lastAssistant = findLastAssistant(msgs)
    const lastFinished = findLastFinishedAssistant(msgs)
    const pendingTasks = collectPendingSubtaskOrCompaction(msgs)

    if (assistantAlreadyFinished(lastUser, lastAssistant) && noPendingToolCalls(lastAssistant)) {
      break
    }

    step++

    if (pendingTasks.topIsSubtask()) {
      handleSubtask(...)
      continue
    }

    if (pendingTasks.topIsCompaction()) {
      const result = processCompaction(...)
      if (result === "stop") break
      continue
    }

    if (lastFinished && contextOverflow(lastFinished)) {
      createCompaction(...)
      continue
    }

    const agent = loadAgent(lastUser.agent)
    const isLastStep = step >= (agent.steps ?? Infinity)
    const messages = insertReminders(msgs, agent)
    const assistant = createAssistantMessage(lastUser, agent)
    const handle = createProcessor(assistant)
    const tools = resolveTools(agent, messages)

    const system = [
      ...environment(model),
      ...instructionFiles(),
      ...availableSkills(agent),
    ]

    const modelMessages = MessageV2.toModelMessagesEffect(messages, model)
    const result = handle.process({
      system,
      messages: [...modelMessages, ...(isLastStep ? [MAX_STEPS_REMINDER] : [])],
      tools,
    })

    if (structuredOutputProduced()) break
    if (result === "stop") break
    if (result === "compact") {
      createCompaction(...)
      continue
    }
  }

  pruneOldToolOutputs(sessionID)
  return lastAssistantMessage(sessionID)
}
```

这段伪代码故意保留了源码中的执行顺序：`step++` 发生在 subtask / compaction 分支判断之前，与 `runLoop()` 的真实实现一致。

### 为什么它会自然变成多轮循环

这个 loop 是**状态驱动**的：

1. 模型先看到 system prompt、历史消息和工具定义。
2. 如果模型发出了 tool call，`SessionProcessor` 会先把这次调用持久化，再执行工具。
3. 工具结果会被写回会话历史，成为 tool part。
4. 下一次 `while (true)` 迭代，会基于最新历史重新构造模型消息。
5. 模型于是能看到自己上一次的工具调用和对应结果，然后决定继续调工具还是直接回答。

正是这个“回放最新状态”的过程，把单次模型调用变成了真正的 agent loop。

关键代码路径：

- loop 退出与重入：`packages/opencode/src/session/prompt.ts:1430-1448`
- tool 解析：`packages/opencode/src/session/prompt.ts:1526-1535`
- system 与消息组装：`packages/opencode/src/session/prompt.ts:1568-1588`
- tool call 持久化：`packages/opencode/src/session/processor.ts:319-376`
- tool result 持久化：`packages/opencode/src/session/processor.ts:378-403`

## 上下文工程

OpenCode 会从四类来源组装上下文，并在需要时做裁剪。

### 1. 系统上下文

每一轮都会拼出一个 system 数组，来源包括：

- `packages/opencode/src/session/system.ts:48-63` 的环境信息
- `packages/opencode/src/session/instruction.ts:106-163` 的 instruction files
- `packages/opencode/src/session/system.ts:65-77` 的可用 skill 列表

也就是说，模型会看到：

- 当前工作目录
- workspace 根目录
- 当前目录是否是 git 仓库
- 平台和日期
- 来自 `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md`、配置文件和远程 URL 的项目 instructions
- 一个 skill 索引，告诉模型有哪些专门工作流可以按需加载

### 2. 历史消息上下文

`MessageV2.toModelMessagesEffect()` 会把 session history 转成 provider 侧真正消费的消息：

- user text 保持为 text
- user files 在支持时转为 file parts
- assistant text 保持为 assistant text
- 已完成工具调用会转成 `tool-*` output parts
- 失败或中断的工具会转成 output errors
- 如果 provider 和 model 没变，reasoning 也可以被回灌

主要代码路径：

- `packages/opencode/src/session/message-v2.ts:729-980`

### 3. 工具上下文

工具并不是裸函数。`ToolRegistry` 先构建带运行时语义的工具集合，随后 `resolveTools()` 再把 session ID、message ID、权限控制、plugin hooks 和执行行为一起接进去。

相关文件：

- `packages/opencode/src/tool/registry.ts:62-180`
- `packages/opencode/src/session/prompt.ts:382-545`

### 4. Skill 上下文

Skill 使用的是惰性加载：

1. `SystemPrompt.skills()` 只先注入可用 skill 列表。
2. 如果模型真的调用 `skill` tool，才会把对应 `SKILL.md` 内容和采样文件注入对话。

相关代码：

- skill 列表：`packages/opencode/src/session/system.ts:65-77`
- lazy load：`packages/opencode/src/tool/skill.ts:14-75`

## 上下文裁剪

当历史越来越长时，OpenCode 会同时使用 compaction 和 pruning。

### Compaction

`SessionCompaction.process()` 会做这些事：

1. 找到更早之前的 compaction summaries
2. 保留最近几轮对话的 tail
3. 对更老的 head 做 anchored summary
4. 把摘要作为 compaction 模式下的 assistant message 保存起来

关键代码：

- summary prompt 结构：`packages/opencode/src/session/compaction.ts:43-78`
- tail 选择逻辑：`packages/opencode/src/session/compaction.ts:247-296`
- compaction 执行：`packages/opencode/src/session/compaction.ts:346-470`

### Pruning

足够旧的已完成 tool outputs 会被标记为 compacted。这样既保留了执行历史，又能把体积很大的工具输出从上下文里裁掉。

相关代码：

- `packages/opencode/src/session/compaction.ts:298-343`

## Reasoning

OpenCode 并不负责实现模型内部的“思考”。它负责的是编排 provider 愿意暴露出来的 reasoning traces。

### Reasoning 如何进入系统

provider 适配层会发出统一化后的 reasoning 事件，例如：

- `reasoning-start`
- `reasoning-delta`
- `reasoning-end`

一个具体例子：

- `packages/opencode/src/provider/sdk/copilot/responses/openai-responses-language-model.ts:1234-1259`

### Reasoning 如何被存储

`SessionProcessor` 会把这些流式事件转成 `ReasoningPart`：

- start：创建 part
- delta：追加文本
- end：补全时间戳和 metadata

相关文件：

- part 结构：`packages/opencode/src/session/message-v2.ts:129-141`
- 事件处理：`packages/opencode/src/session/processor.ts:226-274`

### Reasoning 如何被回灌

OpenCode 重建模型消息时，只有在 provider 和 model 仍然一致的情况下，才会把 reasoning 继续作为 reasoning part 回灌。如果 provider 变了，系统会安全降级，而不会把某个 provider 私有的 reasoning 协议原样喂给另一个模型。

相关代码：

- `packages/opencode/src/session/message-v2.ts:940-954`

### 更工程化的理解

OpenCode 的 reasoning 可以分成三层：

1. 模型内部的 latent reasoning，OpenCode 看不见
2. provider 暴露出来的 reasoning summary，OpenCode 可以持久化
3. 通过调工具、读结果、做决策而外化出来的 agentic reasoning

第三层才是系统视角下最重要的部分：loop 把“思考”外化成了一连串可执行步骤。

## 一次真实请求循环

请求示例：

> 找出 OpenCode 的核心 Agent 循环，并解释它如何管理 tools 和 skills。

### Round 0

- 用户消息入库
- `SessionPrompt.loop()` 启动 `runLoop()`

相关入口：

- `packages/opencode/src/session/prompt.ts:1630-1634`

### Round 1

模型会看到：

- provider prompt
- environment block
- instruction files
- available skills
- conversation history
- tool definitions

这时它通常会决定调用 `glob`、`grep`、`read` 之类的工具。

随后会发生：

- `SessionProcessor` 先记录 tool call
- 工具被执行
- 工具结果被写回 assistant message

因为 assistant 的 finish 是 `tool-calls`，所以 loop 不会退出，而是继续下一轮。

### Round 2

下一次迭代会根据最新 session state 重建消息。此时模型能看到：

- 自己上一次发出的 tool call
- 工具返回的输出
- 仍然可用的工具集合（除非 agent 权限在中间发生变化）

然后它会做两种选择之一：

- 继续调更多工具，进入下一轮
- 或者直接综合成最终回答，结束 loop

这就是 OpenCode 多轮执行最核心的模式：

`模型 -> 工具调用 -> 工具结果 -> 重建上下文 -> 模型`

## 总结

- `runLoop()` 才是真正的运行时中心
- tool call 是形成多轮执行的回边
- 上下文由 environment、instructions、skills、messages 和 tools 一起组装
- compaction 与 pruning 用来把 prompt 控制在模型上下文窗口之内
- reasoning 由 provider 或模型产生，但 OpenCode 会把它持久化并在后续回合中回放
